# TrainCheck agent pilot: adaptive latent reasoning

Status: protocol frozen before solver trials; results pending.

The decision is whether TrainCheck gives research agents useful diagnostic
evidence that justifies a larger evaluation. This is a reduced-compute development
pilot, not an official RSI benchmark submission or leaderboard score.

## Task and scope

The public Scale AI RSI repository is pinned to
`aa82cfc29e541e68b5fb79d789b3f09227851739`, task
`tasks/adaptive-latent-reasoning`. Its public local trainer already supports CPU
execution. The unchanged 51,335-parameter looped Transformer learns prefix
addition/subtraction modulo seven with one through five operations. The original
model, eight training loops, data generator and tensor-program interpreter are
retained. Agents edit a loss function and optionally optimizer equations through
that interpreter. They cannot change the model, data, runner, training profile or
evaluator. This pilot fixes inference depths to `[1, 2, 4, 4]` to isolate training
changes; it does not evaluate the task's full inference-policy search space.

The official task uses an H100, batch 4,096, up to 50,000 updates and a signed
trusted training service. This pilot uses labmach CPU, batch 64 and 10,000
updates, the public content-hash partition and unsigned local checkpoints.
Learning-rate warmup is 100 updates and cosine decay ends at 10,000. The initial
learning rate, backbone, optimizer defaults and baseline depth weights stay as
in the public task. Data pool construction is disabled in favor of the upstream
on-demand sampler. Runtime differs from the official lockfile: the existing
Python 3.11.4 / Torch 2.16 development CPU environment is used with an isolated
safetensors 0.8.0 overlay. Exact profiles and hashes are retained with artifacts.

## Calibration, before solver access

The built-in objective at 200, 1,000 and 3,000 updates stayed near chance on the
public development panel. A 10,000-update run using the exact public
`baseline_research.py` through the actual tensor-program interpreter completed
in 132.716 seconds of training (134.21 seconds process wall time). Development
accuracy at depths 1/2/4/8 was 22.220/24.173/23.548/23.235 percent. Gains were
concentrated in one- and two-operation expressions; longer expressions remained
near chance. This is one deterministic training run, not a repeated timing
estimate. The one-operation development stratum has only 17 distinct examples;
macro averages weight it equally with the four larger strata.

## Comparison protocol

- Three matched pairs of fresh agents, trial order C1/T1, T2/C2, C3/T3. Each
  receives the same public source interface, baseline program, baseline
  development feedback, frozen training profile and optimization objective.
- All solver agents start without the parent conversation. They use the same
  inherited model/effort configuration. No solution, repository task metadata
  containing solution explanations, private verifier, other trial or final-test
  result is provided. The operator inspected task metadata during selection;
  that context is deliberately excluded from solver prompts.
- Each agent may submit at most two candidate programs for 10,000-update runs.
  Failed requests consume this allowance. Treatment agents additionally receive
  the TrainCheck skill and may request one short diagnostic rerun for a candidate.
  This additional computation is measured and included in cost reporting.
  Both arms may select the supplied baseline instead of a candidate.
- The intended reasoning window is 15 minutes per solver, excluding time queued
  for shared compute. The client enforces candidate and diagnostic counts;
  agent reasoning/token limits are not mechanically enforced by this native
  subagent interface. Actual elapsed time and any overrun will be reported.
- Candidate training is serialized on the same four idle performance cores
  (8, 10, 12, 14). Original upstream code uses four Torch threads. A shared lock
  prevents candidate/diagnostic overlap. Process wall time includes queue and
  transfer costs; training-body time is reported separately.
- Final selection is written before held-out scoring. The operator then uses
  the original model, public generator's test partition, seed 20261030 and up to
  512 distinct examples per operation stratum. No candidate is tuned on these
  results. Final scoring uses upstream accuracy/FLOP accounting and reward
  formula for the fixed policy; it is still a pilot metric, not an official
  score or trusted-service receipt.

## TrainCheck treatment and interpretation

Reference inference uses the unmodified public baseline program and an explicit
three-update probe. Target probes use the same runtime, model and batch size.
The probe's `total_steps` is three, so step-dependent candidate programs may
behave differently from their full 10,000-update runs. This limitation is exposed
to solvers. Tracing is API-only; no claim of variable-tracker or complete gradient
invariant coverage is made. The interpreter rejects Tensor subclasses, so the
model tracker is not silently enabled.

The adapter checks unmodified trainer source and traces only the training body.
Full reference tracing is installed before the research interpreter captures
Torch callable references. Plain/reference controls must match model, gradient,
optimizer, buffer, loss, Torch RNG and local data-generator state. Unseeded
global Python/NumPy RNGs must remain unchanged within each run. Invariants are
frozen before candidate checks, and no rule is discarded to reduce alarms.
FunctionLead/FunctionCover relations are excluded as in the validated bounded
offline workflow; remaining families are retained.

An invariant violation means a difference from reference behavior. Loss and
optimizer changes are expressly allowed, so many differences may be legitimate.
The treatment receives the fresh healthy-run report and full evidence paths to
help distinguish such differences. Checker exit code zero does not mean no
violations; errors, dormant rules, skipped checks and missing evidence stay
explicit. Both ordinary training and diagnostic failures are retained.

## Decision criteria

Record task success, selected-program identity, development and held-out reward,
all attempted candidates, measured training/diagnostic/setup cost, actual tool
use and whether any diagnostic changed an agent decision. A useful mechanistic
signal is an agent using relevant evidence to correct an unintended training
behavior, followed by independent validation. Fewer alarms alone do not count
as improvement. A higher score in one of three pairs does not establish a
general effect or statistical significance.

If diagnostics are unused, irrelevant, dominated by healthy/reference-mismatch
alarms or add cost without improving decisions, the recommendation is to pause
broader performance work and target the demonstrated integration/coverage gap.
If the treatment shows a reproducible useful mechanism, select additional tasks
and increase repeats before making claims about model quality or efficiency.

## Artifacts and engineering checkpoint

Local large artifacts: `outputs/rsi-pilot-20261030/` in the experiment owner's
canonical TrainCheck checkout. Remote: labmach
`/home/yuxuan/experiments/traincheck-rsi-pilot-20261030/`. Only allowlisted public

The pilot branch integrates the reviewed #163 changes that had not reached main.
Composed regression checks passed 134 tests on labmach. The exportable skill and
report helper passed ten tests, explicit strict typing and configured checks.

control produced 87 active passes and four containment alarms, with matching
recorded losses. That smoke is separate from this RSI task.
